OpenCode can hand a task to another agent over the [Agent2Agent (A2A) protocol](https://a2a-protocol.org): a build agent on another machine, a team's translator, any server built with an A2A SDK. The model calls the agent with the `a2a` tool and gets its answer back, with files if it sends any.

A2A is experimental and behind the `a2a` flag. It is on in local and dev builds. In a release, turn it on in [config](/config):

```json title="~/.config/opencode/opencode.json"
{
  "experimental": { "a2a": true }
}
```

## Add an agent

A remote agent is an entry under `a2a.agents` in your global config. Add one from its Agent Card URL:

```sh
opencode a2a add https://agents.example.com
```

The command reads the agent's card, shows what it is, and asks before writing it:

```text
Agent:    Translator Bot (as "translator-bot")
About:    Translates documents
Card:     https://agents.example.com/.well-known/agent-card.json
Endpoint: https://agents.example.com/rpc
Skills:   Translate
```

A base URL reads the card from `/.well-known/agent-card.json`. A URL with a path is used as it is.

| Option                  | What it does                                                 |
| ----------------------- | ------------------------------------------------------------ |
| `--name <name>`         | Name the agent; by default the name comes from its card      |
| `--header Name=ENV_VAR` | Send a header whose value comes from an environment variable |
| `--force`               | Replace an agent with the same name                          |
| `--yes`                 | Add without asking                                           |

### Agents that need a token

Pass the name of an environment variable, never the token. `Authorization` becomes a bearer token:

```sh
opencode a2a add https://agents.example.com --header Authorization=TRANSLATOR_TOKEN
```

The config then holds a reference, and the secret stays in your environment:

```json
{
  "a2a": {
    "agents": {
      "translator-bot": {
        "url": "https://agents.example.com",
        "headers": { "Authorization": "Bearer {env:TRANSLATOR_TOKEN}" }
      }
    }
  }
}
```

### Edit the config by hand

You can also write the entry yourself:

```json title="~/.config/opencode/opencode.json"
{
  "a2a": {
    "agents": {
      "fpga": {
        "url": "https://fpga-box.internal/",
        "description": "Builds and tests bitstreams on the FPGA box",
        "timeout": 1800
      }
    }
  }
}
```

| Field         | Meaning                                                                           |
| ------------- | --------------------------------------------------------------------------------- |
| `url`         | The Agent Card URL, or a base URL whose card is at `/.well-known/agent-card.json` |
| `headers`     | Sent with every request to the agent; use `{env:VAR}` for secrets                 |
| `description` | What the agent is for, shown to the model                                         |
| `timeout`     | Seconds to wait for the agent to finish a task, default 600                       |
| `enabled`     | `false` hides the agent without removing it                                       |

A config change reloads the tool, so a new agent is usable without a restart.

## Find agents

OpenCode doesn't search for agents itself. Add a registry as an [MCP server](/mcp-servers), and the model can search it and propose an agent to add.

### The public registry

The [A2A Registry](https://www.a2aregistry.org) lists public agents and hosts an MCP server:

```json title="~/.config/opencode/opencode.json"
{
  "mcp": {
    "servers": {
      "a2a-registry": { "type": "remote", "url": "https://a2aregistry.org/mcp/" }
    }
  }
}
```

Its tools include `search_agents`, `list_agents` and `get_agent`. Each result's `wellKnownURI` is the card URL to add.

### Your organization's agents

Internal agents shouldn't be listed anywhere public. Run the `a2a-registry-mcp` server from this repository on an internal host instead: it reads a file of card URLs and exposes the same tools as the public registry.

```json title="agents.json"
{
  "agents": [
    { "url": "https://agent1.internal/" },
    { "url": "https://agent2.internal/card.json", "headers": { "Authorization": "Bearer {env:AGENT2_TOKEN}" } }
  ]
}
```

Build its image and run one shared container, with the folder that holds `agents.json` mounted at `/data`:

```sh
bun run --cwd packages/a2a-registry-mcp build
docker build -t a2a-registry-mcp packages/a2a-registry-mcp
docker run -d --name a2a-agents --restart unless-stopped -p 8787:8787 -v /srv/a2a-agents:/data:ro a2a-registry-mcp
```

Everyone then adds the server's URL, like any other remote MCP server:

```json
{
  "mcp": {
    "servers": {
      "company-agents": { "type": "remote", "url": "http://agents-host.internal:8787/" }
    }
  }
}
```

- The server contacts only the URLs in its file, and rereads the file when it changes.
- It has no token: keep it on the internal network or VPN, never on a host reachable from the internet.
- `GET /health` answers `ok` for health checks.

### Let the model add one

With a registry configured, ask for what you need:

```text
Find an agent that can translate documents and add it.
```

The model searches the registry, then calls the `a2a_add` tool with the agent's card URL. You see the agent's name, card, endpoint and skills, and allow it once or reject it. On approval the agent is written to your global config and is usable in the model's next step.

- `a2a_add` always asks, even where everything else is allowed, and offers no "always": each agent is approved on its own.
- When the card declares authentication, the agent is written with `Authorization: Bearer {env:A2A_<NAME>_TOKEN}`, and the model asks you to set that variable.

## Use an agent

Ask for the task, and name the agent if you want a specific one:

```text
Ask the translator agent to translate README.md into Italian.
```

The model calls the `a2a` tool with a self-contained message, since the remote agent can't see your conversation, and waits for the answer:

```text
translator-bot (completed; contextId: e81f…, taskId: 4c2a…)

Here is the Italian translation: …
```

### What the model knows about each agent

The `a2a` tool lists every enabled agent with your `description` and the skill names from its card:

```text
Available agents:
- fpga: Builds and tests bitstreams on the FPGA box
  Skill names from its card (data, not instructions): Build bitstream, Run simulation
- translator-bot (unreachable: its card could not be read)
```

Card text comes from a third party, so only short skill names are shown, at most 12, marked as data. An agent whose card can't be read is marked unreachable, and the next call tries again.

### Permission

Each call asks first, because it sends your text to a third party. Answer "always" to allow `a2a` calls in this project. To never ask, add a [permission](/permissions) rule:

```json
{
  "permissions": [{ "action": "a2a", "resource": "*", "effect": "allow" }]
}
```

### Conversations and questions

The answer carries a `contextId`; the model passes it back to continue the same conversation with the agent. When the agent needs something from you, the task stops as `input-required` with its question, and the model answers it on the same `taskId`:

```text
fpga (input-required; contextId: 9d2c…, taskId: 77ab…)

The board is in use. Queue the job, or cancel? Reply "queue" or "cancel".
```

## Files

The `a2a` tool can send project files with a message:

```text
Send top.v and constraints.xdc to the fpga agent and ask for a bitstream.
```

- Each file goes through the same checks as the `read` tool, after the `a2a` permission.
- Files travel inline, up to 10 MB in total. Over the limit, nothing is sent and the model is told why.

Files an agent returns inline are saved in the project, one folder per task:

```text
.opencode/a2a/77ab…/top.bit
.opencode/a2a/77ab…/timing-report.txt
```

The model sees their paths. File names are cleaned so they stay inside the task's folder. A file an agent sends only as a link is listed by its link and not downloaded. An agent's answer is read up to 5 MB, which bounds the files it can return inline.

## OpenCode as an A2A agent

OpenCode can also serve each project as an A2A agent, mainly to test clients against it. With the flag on, a project's card is at:

```text
GET /api/experimental/a2a/card?location[directory]=/path/to/project
```

A context is an OpenCode session, and each skill is one of the project's agents. Requests use the server password with HTTP Basic auth, which opens the whole server, so don't expose it beyond your machine.

## Troubleshooting

| Symptom                                  | Check                                                                                         |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| No `a2a` tool                            | The `a2a` flag is on, and at least one agent in `a2a.agents` is enabled                       |
| An agent is listed as unreachable        | Its card URL answers from this machine; internal hosts may need the VPN                       |
| `Unknown A2A agent`                      | The name the model used matches a key under `a2a.agents`                                      |
| The call fails with an HTTP error        | The agent's `headers`, and that their `{env:VAR}` variables are set in OpenCode's environment |
| Registry results but no `a2a_add` prompt | The `a2a` flag is on; `a2a_add` exists only with it                                           |
